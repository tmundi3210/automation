## SLICE 3 — Review-frequency control + AnkiConnect push + Google Calendar reminders
**Goal.** A plain-language workload control (no new math), one-way card push into local Anki, and study-window reminders as Google Calendar events. Rides on Slice 0's Secrets + outbox.

**What to build.**
- **A.1 Review-frequency control (no new math).** The single honest workload dial already exists: `desired_retention` 0.70–0.97 [FACT — APP_RECON §5.11]; scheduler doctrine: it is THE knob, a raw interval multiplier would fight FSRS, warn above 0.90 [FACT — FEATURE_PLAN P3 / SPECIALIST_RECON §1]. Screen behavior: one "How much do you want to study?" panel = outcome-labeled retention dial ("fewer reviews, forget more ↔ more reviews, forget less") with live workload delta estimate + the two other honestly tunable levers, `new_per_day` and `daily_minutes` (enforced per S0.4). Nothing else is tunable without fighting the algorithm — say so in the UI. FSRS parameter/desired-retention changes **inside Anki** cannot be set via AnkiConnect (no such action exists [FACT-source: AnkiConnect v6 README grep, via mirror]) — route those to Anki's own Deck Options UI; never invent an action (extint escalation trigger).
- **A.2 AnkiConnect push — bridge topology.** AnkiConnect answers only on `http://127.0.0.1:8765` with Anki running [FACT-source: git.sr.ht/~foosoft/anki-connect README, via mirror]; a Base44 cloud backend can never reach it [FACT — EXTERNAL_RECON cross-cutting]. Two honest routes, in order: **(1) browser route** — the app's frontend (running on the owner's machine) calls it directly; AnkiConnect has a CORS allowlist and an in-Anki permission popup for new origins [FACT-source: same README]; success from the deployed origin is [ESTIMATE, medium-high] — [METHOD: one `deckNames` call from the deployed app's origin; owner clicks "allow" once]. **(2) local-bridge route** — a small helper on the owner's machine (folds into Slice 5's MCP bridge) relays app→AnkiConnect. If (1) fails, ship (2); never a direct cloud call.
- **A.3 Push contract.** One-way, app→Anki, per deck/selection. Notes created via `addNote`/`addNotes` (deck, model, fields, tags, duplicate options) [FACT-source: same README]. Idempotency: each pushed card carries its app card-id in a dedicated field/tag; pre-check with `canAddNotes` and duplicateScope so a retried push cannot double-create [FACT-source: same README for those actions; the keying scheme is app design]. Pushed notes are labeled "managed by the study app — review here OR there, not both" (two scheduling authorities is the known risk [FEATURE_PLAN P3]). Workload influence on the Anki side is limited to documented actions: `saveDeckConfig` per-day limits, `setDueDate`, `forgetCards` [FACT-source: same README] — nothing more.
- **A.4 Google Calendar reminders.** Timed nudges = Calendar **events**, full stop: there is no public Google Reminders API (reminders migrated to Tasks in 2023) and Tasks `due` is date-only, time discarded [FACT-source: workspaceupdates.googleblog.com 2023-06 + developers.google.com/tasks reference, via snippets]. After each nightly plan (S0.1), a backend function inserts tomorrow's study windows via `events.insert` with `reminders.useDefault=false` + popup overrides (minutes ≤ 40320, max 5/event) [FACT-source: developers.google.com Calendar concepts/reminders + events/insert, via snippets]. Auth: OAuth 2.0 authorization-code flow with token refresh — a pasted key cannot access a private calendar [FACT — EXTERNAL_RECON §3]; least-privilege scope `https://www.googleapis.com/auth/calendar.events`, not full `calendar`. Whether Base44's Google Workspace connector covers Calendar scope is [UNKNOWN — METHOD: check the workspace connector list; fallback: manual OAuth in a backend function with client id/secret + refresh token in Secrets]. Reliability: inserts flow through the outbox; the stored `external_id` prevents duplicate events on retry; a plan re-run updates/deletes its own prior events (keyed by plan date) rather than stacking new ones. Re-consent UX on token revocation is required, loud not silent.

**Acceptance checks.** The retention dial changes only `desired_retention` and warns above 0.90; a retried Anki push never double-creates a note (verified via `canAddNotes` pre-check); a plan re-run leaves exactly one set of calendar events for that date; token revocation surfaces a visible re-consent prompt.

**Owner approval gates.** `credential_add` (Google OAuth grant — owner performs consent personally), `external_send` (first calendar event written; owner reviews a trial week per FEATURE_PLAN P3 gate), Anki push direction approved by owner (one-way) before first `addNotes`.
