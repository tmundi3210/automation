## SLICE 5 — MCP bridge (Codex first) + Ollama Cloud model picker — OWNER'S TOP PRIORITY
**Goal.** Coding agents (Codex first; Claude Code, Grok as options) read/write the study system through one local MCP bridge; the app's own LLM calls route through an exactly-two-model Ollama Cloud picker with cost visibility. May run right after Slice 2 (needs only a stable data model), in parallel with Slices 3–4.

**What to build.**
- **C.1 App-side API.** Backend functions exposed as authenticated custom endpoints (supported per Base44 docs [FACT-source: docs.base44.com backend-functions overview, via snippet — verify in-app]): reads (due summary, weaknesses, tomorrow's plan) and writes (card create, pipeline trigger). Auth: a static bearer token in Secret `MCP_BRIDGE_TOKEN`, checked server-side. **Read-only by default**; each write capability is unlocked by the owner one at a time and every agent write is journaled append-only (sysloops rule; FEATURE_PLAN P5 risk a).
- **C.2 The bridge (runs on the owner's machine).** One small local MCP **server** translating MCP tool calls into those endpoints; it serves all three CLIs because all three are MCP clients. **Codex first:** register with `codex mcp add <name> -- <command>` (or streamable-HTTP URL); servers live in `~/.codex/config.toml`; `/mcp` in the TUI lists them [FACT-source: developers.openai.com/codex/mcp, via snippet]. Codex can itself serve via `codex mcp-server` [FACT-source: developers.openai.com/codex/cli/reference, via snippet] — the Slice 7 image-generation direction. **Claude Code:** `claude mcp add --transport http|sse|stdio`, project-scope `.mcp.json`; can serve via `claude mcp serve` [FACT-source: code.claude.com/docs/en/mcp, fetched directly]. **Grok Build:** native MCP client, reads the same `.mcp.json`/Claude-style configs unchanged [FACT-source: x.ai/news/grok-build-cli + x.ai/cli, via snippets]; Grok-as-server [UNKNOWN — METHOD: docs.x.ai from an unblocked network]. Ship one shared project-scope `.mcp.json` so all three attach identically. The bridge holds `MCP_BRIDGE_TOKEN` in local config only — never in the repo.
- **C.3 Ollama Cloud auth + surfaces.** Key created at ollama.com/settings/keys, sent as `Authorization: Bearer`; keys don't expire, revocable [FACT-source: docs.ollama.com api/authentication.mdx via docs-source mirror]. Stored as Secret `OLLAMA_API_KEY`, used only in backend functions. Bases: native `https://ollama.com/api`, OpenAI-compatible `https://ollama.com/v1/` (chat completions w/ streaming, tools, JSON mode, vision) [FACT-source: introduction.mdx + openai-compatibility.mdx + droid.mdx, same mirror]. "Already signed in" path (`ollama signin` → auto-authenticated localhost calls) helps only components on the owner's machine — the bridge may use it; the Base44 backend cannot see localhost and needs the pasted key [FACT-source: cloud.mdx + authentication.mdx]. Browser→localhost-Ollama from the deployed origin: [UNKNOWN — METHOD: one test fetch].
- **C.4 Model picker — exactly two active.** Settings panel lists the **live** catalog via `GET https://ollama.com/api/tags` (or `/v1/models`) at open [FACT-source: cloud.mdx + openai-compatibility.mdx]; never a hardcoded list — several cloud models retire 2026-07-15, one week out [FACT-source: cloud.mdx deprecations table]. Owner activates **exactly two** models, role-labeled generator + grader [source: FEATURE_PLAN P5]; activating a third forces an explicit swap. No model is named in this plan: any name is a live-query result (extint escalation trigger). **Retirement handling:** on each list refresh, a pinned model missing/deprecated ⇒ selection marked invalid, calls to it stop, owner is asked to re-pick — never a silent substitute. **Fallback chain (loud):** role's primary → the other active model → existing `Core.InvokeLLM` (both current LLM calls use it today with no model choice [FACT — APP_RECON §5.8]) → surfaced, logged failure. No silent empty/fabricated result ever enters learning data. Golden-set drift checks gate the chain; rubric authorship belongs to the task-owning specialists (extint boundary).
- **C.5 Cost visibility.** Ollama pricing/rate tiers [UNKNOWN — METHOD: ollama.com/cloud + account settings with the owner's key]. Until priced: log per-call token usage from API responses into the existing never-set `SystemMetrics.llm_cost_usd` slot's companion counters [FACT that the field exists unused — APP_RECON §2]; show tokens-per-day in Settings; convert to dollars only after a verified price, tagged with its source. `spend` gate before any paid tier is enabled.

**Acceptance checks.** A read-only Codex session answers "what am I weak on?" end-to-end via the bridge; a write attempt before its capability unlock is rejected and journaled; deactivating/retiring a pinned model stops calls to it and prompts a re-pick (never a silent substitute); every agent write has an append-only journal row; token usage per day is visible in Settings.

**Owner approval gates.** `credential_add` (OLLAMA_API_KEY, MCP_BRIDGE_TOKEN), owner runs one end-to-end read-only Codex session before any write unlock (FEATURE_PLAN P5 gate), per-write-capability unlock = owner action, `spend` for paid tiers; owner picks the initial 2 active models personally.
