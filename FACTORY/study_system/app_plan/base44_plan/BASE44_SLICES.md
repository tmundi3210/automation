## SLICE 0 — Platform foundations (everything else rides on these)

**Goal.** A real scheduler, correct day keys, exact counts, an enforced new-card allowance, a single credential store, and a reliability spine for every external effect.

**What to build.**
- **S0.1 Scheduler.** Today nothing recurs: "nightly" = the Dashboard button [FACT — APP_RECON §3b, risk 1]. Wire `runPipeline` to a Base44 Automation on a daily schedule (Automations run backend functions on schedules or DB events [FACT-source: docs.base44.com backend-functions overview, via snippet — verify in the workspace before relying on it; exact scheduling UI/limits UNKNOWN, METHOD: open workspace → Automations and confirm a daily invoke of `runPipeline`]). Overlap-safety is mandatory: the pipeline is already keyed by `run_date` delete-then-recreate [FACT — APP_RECON §3b], so add a per-run-date guard row (skip if a PipelineRun for that key is in progress/complete) so a schedule firing while the manual button runs cannot double-apply. Keep the button as manual override. Schedule fires in the **owner's local day** (see S0.2), after local midnight.
- **S0.2 Day-key fix.** Day keys are computed in UTC while the calendar draws local days [FACT — APP_RECON risk 5]. Behavior: one shared day-key rule — an explicit `timezone` field in Settings (owner-set, IANA name), and every day-key producer/consumer (Dashboard, submitReview's DailyPlan write, runPipeline stages, DayBoxCalendar) derives the day from that timezone. Acceptance: a review submitted at 23:00 local lands on today's plan, not tomorrow's.
- **S0.3 Lift the 500-row caps.** Pipeline and dashboard queries silently truncate at 500 rows [FACT — APP_RECON risk 3]; at the planned 2000+ cards stats under-count. Behavior: every capped query becomes a paginated loop to exhaustion (or a server-side aggregate), and each pipeline stage records rows-scanned in PipelineRun so truncation is observable, never silent. Base44 pagination semantics [UNKNOWN — METHOD: verify SDK list/filter paging in the workspace].
- **S0.4 Enforce `new_per_day`.** The review queue takes the first 30 due states ignoring the new-card allowance [FACT — APP_RECON risk 7]. Behavior: queue assembly counts new-state cards introduced today (from Revlog) and admits new cards only up to `Settings.new_per_day`; reviews of seen cards are never blocked. Acceptance: with new_per_day=5 and 40 due new cards, at most 5 new cards enter a day's queue.
- **S0.5 Secrets are the ONLY credential store.** Every external credential lives in a per-app Secret read server-side inside a backend function [FACT-source: docs.base44.com/Integrations/Using-integrations, via snippet] — never in client code, never in the two-way-synced repo (sync would leak it [FACT-source: docs.base44.com GitHub-sync pages]). Named slots in the master plan's integration table; empty slots render as "not configured" in Settings, showing slot name only, never values. Rotation: on suspected exposure, rotate and fire the `security_alert` gate. Filling any slot passes the `credential_add` gate (owner pastes it personally).
- **S0.6 Reliability spine (new entity: `OutboxItem`).** Every must-not-lose external effect (Anki note push, Calendar event, WhatsApp send) persists intent first: `OutboxItem {target, action, payload, idempotency_key, status queued|sent|failed|dead, attempts, last_error, external_id}`. A drainer Automation retries only retriable classes (timeouts, 5xx, 429) with exponential backoff + jitter within a timeout budget; exhausted items go `dead` (DLQ) and surface in UI; per-target circuit breaker fails fast during a sustained outage. Non-idempotent POSTs are never blindly retried — the idempotency key dedupes (exactly-once is unachievable; at-least-once + idempotency is the contract).

**Acceptance checks.** The S0.2 and S0.4 acceptance lines above; a scheduled run and a same-night button press yield one applied run; a killed external send retries to `sent` or lands in the visible DLQ, never duplicates; no secret value ever appears in client code, repo, or UI.

**Owner approval gate.** `schedule_enable` — the owner enables the daily Automation in the workspace themself; `credential_add` for any slot filled. No other external action in this slice.

## SLICE 1 — Explainability layer (ships early, zero dependencies)

**Goal.** Every non-obvious label, number and code explains itself honestly at four depths. Scope: WHAT each surface must say and at which disclosure depth — not pixels, not scheduling math. The app today has zero tooltips and no guide layer of any kind [FACT — APP_RECON §5.9], so this is pure addition. No new entities; persistence of seen/dismissed hints may use one small field on the existing Settings entity or client storage (builder's choice; must survive reload).

**What to build.**

**1. The four-rung disclosure ladder.** One ladder, single-sourced: every concept is authored ONCE as a Guide-page entry; rungs 1–3 quote or deep-link into it so they can never contradict each other.
- **Rung 1 — inline caption**: a tiny always-visible line under the label. Essential operating meaning lives HERE, never behind a reveal.
- **Rung 2 — hover card ("thinking cloud")**: 2–3 sentences; accessible spec in item 4.
- **Rung 3 — "more" icon panel**: in-context expandable panel, paragraph-plus with a concrete example; stays open until closed.
- **Rung 4 — Guide page**: canonical catalog entry with a stable anchor per concept; searchable.
Every non-obvious element carries visible information scent (small "i"/"?" or dotted underline). Depth budget is proportionate: trivial controls get rung 1 only; honesty-critical numbers earn all four.

## SLICE 2 — Planner dynamics (the calendar comes alive)

**Goal.** Day-click detail view, next-day-only detailed planning, enforced gating with regression, and evidence-based weakness auto-resolution. Ownership split (binding throughout): **sched** owns all scheduling math and queue/plan assembly, **learner** owns mastery estimation, gating evidence and weakness diagnosis, **engage** owns every visual render rule.

**What to build.**

**P2.0 Ride-along prerequisites** — Slice 0 delivers most of them; verify before building: the canonical local day-key (S0.2), full pagination (S0.3), enforced `new_per_day` (S0.4), and the daily scheduled run (S0.1; fallback until enabled: owner's morning button press). One prerequisite is P2-specific:
- **One plan writer.** Dashboard-load currently creates/updates DailyPlan and races submitReview [FACT — APP_RECON risk 6]. After this slice: only the pipeline writes plans; submitReview only increments `done_units`; Dashboard only reads.

**P2.1 Date-click day-detail view** (engage renders, sched supplies). Day boxes have no click handler today [FACT — APP_RECON §5.10]. Add: clicking any day-box opens a day-detail panel. Engage's day-box brief stays **binding law for the box itself** — white empty box + day number, single green download-bar fill, floored 5% steps, tick only at true 100% [FACT — owner brief, already encoded as `daybox_state` 0..20 in APP_RECON §4b]. The detail panel is additive and must not alter box semantics.
- **Past day:** what actually happened — reviews done vs planned (Revlog + DailyPlan), per-topic counts, any gating/regression events logged that day. Whether a past incomplete box freezes at its final % or grays out is an owner-unresolved build-time decision [UNKNOWN — engage brief]; store the frozen pct either way (switch-either-way design).
- **Today / tomorrow:** the plan — topic list (concept names of cards due that day) with per-topic counts (review / new / probe) and an assigned **time window** each. Honesty: the app stores no time-of-day anywhere [FACT — APP_RECON]; windows are a NEW planner output = `daily_minutes` split into 2–3 named windows (e.g. Morning / Evening) [ESTIMATE — design default; the split rule is decided at the owner gate]. Minutes-per-topic derive from the count × measured per-card throughput once revlog durations exist; until measured, a labeled [ESTIMATE] default — never presented as measured.
- **Days beyond tomorrow:** coarse only — projected load band from the Planner curve, rendered in a style visibly distinct from actual completion that can **never show a tick or a green fill** (forecast ≠ done — engage's forecast rule). No per-topic detail exists for those days, so none is shown.
- Effort (day-box %) and mastery (course/learner-model %) stay separate metrics, never merged (engage's effort-vs-mastery split).

**P2.2 Next-day-only detailed planning** (sched owns). Doctrine: back-plan detail only where evidence exists; the far future gets feasibility, not fiction (sched refuses days-to-mastery formulas and pass probabilities — those never appear anywhere).
- **Reads:** today's + yesterday's Revlogs (grades, elapsed, durations, correctness), CardStates due tomorrow (FSRS-6 via ts-fsrs is already the scheduler [FACT — APP_RECON §1]), open Weakness rows + fresh diagnoses (P2.4), gate states (P2.3), Settings (`daily_minutes`, `new_per_day`, `desired_retention`).
- **Writes: the DailyPlan artifact for tomorrow** — extended from today's bare `planned_units` [FACT — pipeline stage 4, APP_RECON §3b] to carry a per-topic breakdown: for each concept due tomorrow, {topic, review count, new count (0 if gated), probe count, assigned window, why-line (e.g. "12 due · gated: base weak")} plus a computed-at stamp. Rerun-safe: keyed by day-key, upsert not duplicate; `done_units` never overwritten by a re-plan.
- **Budget rule:** reviews first (FSRS due output is never trimmed to favor new material), then probes, then new cards up to `new_per_day`, all capped by `daily_minutes` — the minutes budget is the true bottleneck and binds last-in-first-out (new cards yield first, then probes; due reviews spill visibly to a non-punitive backlog note, never silently dropped).
- **Beyond tomorrow:** only the Planner's coarse feasibility curve (go/tight/no_go). Honesty carry: `planExam`'s ×2.3 interval ladder is a heuristic, not FSRS simulation [FACT — APP_RECON risk 12]; label its curve [ESTIMATE] in-UI; [METHOD] later replace with ts-fsrs simulation over real CardStates. Do not build multi-day detailed plans — detail decays into guesswork past one day.

**P2.3 Gating + regression** (learner decides, sched enforces). The diagnosis already SAYS "block new cards until prereq mastery ≥ 0.6" but it is prose only — nothing enforces it, and the review queue ignores `new_per_day` entirely [FACT — APP_RECON §4a rule 2, risk 7].
- **Who decides:** learner's nightly diagnosis emits gate verdicts as data (per concept: gated true/false, reason, evidence). Sched's queue assembly and P2.2 planner consume them. Neither layer re-derives the other's call.
- **Gate rule:** a concept-group does not receive NEW cards while (a) any declared base/prerequisite concept has BKT mastery < 0.6 [FACT — the prose rule's own threshold; owner-tunable at the gate], or (b) fallback: the concept's own mastery is weak — needed because `ConceptEdge` rows are never created by any code today [FACT — APP_RECON §5.5]. This slice therefore adds a minimal manual "A is the base of B" declaration in the Library (creates prereq ConceptEdge rows; must call Slice 6's `writeEdge` once it exists); edge-based gating activates only where edges exist.
- **Gating never blocks reviews** — already-seen cards keep their FSRS schedule untouched (non-punitive contract; engage boundary + sched's scheduler-output-is-not-degraded rule).
- **Regression:** the gate re-applies automatically when a base concept's mastery falls back below threshold **and** its uncertainty is low (learner's uncertainty gate: a low score on an under-sampled concept routes to probes, not to regression — never thrash the plan on noise). A regressed group's plan entry reverts to base-concept reviews + probes; its queued new cards are skipped, not deleted.
- **Uncertainty measure honesty:** exact Glicko RD equations are [UNKNOWN — egress-blocked source; learner boundary]; use the labeled RD-like stand-in (answer count + recency). The existing `elo_theta_sd` decays ×0.97 toward a floor regardless of outcomes [FACT — APP_RECON §3a] — that is wrong per doctrine; uncertainty must GROW with inactivity. Fix rides with this sub-slice.
- **Safety valves:** every gate is per-concept overridable in the UI (a wrong hand-declared edge must not dead-lock a topic), and all gate/regress events appear on the day-detail view — nothing hidden.

**P2.4 Auto-resolution of weaknesses** (learner owns; replaces Mark-Resolved). Current lifecycle is broken: duplicates accumulate across days, same-day reruns wipe "resolved" marks, `probing` and `probe_card_ids` are write-only, Mark-Resolved changes nothing but a status flag [FACT — APP_RECON §4a, risk 8].
- **Lifecycle states:** `open → probing → resolved`, plus `regressed → open` (reopened by new evidence) and `snoozed`. One row per (concept, cause), **upserted across days** — a rerun updates evidence on the existing row; it never deletes-and-recreates by run_date, so reruns are safe and resolution timestamps survive.
- **Evidence rule (resolve):** a weakness auto-resolves when ALL hold: (1) concept BKT mastery back ≥ threshold; (2) probe items on that concept answered correctly at **≥ 2 spaced points — distinct days** [ESTIMATE — design default per trend-not-snapshot; tune from real runs at the owner gate], because delayed retrieval, not same-session fluency, is the learning signal (learner dominance rule); (3) evidence is format-weighted — a correct 4-option MCQ counts less than a typed/free-recall correct (IRT guessing floor c≈0.25), so at least one non-MCQ probe correct is required where the concept has any [ESTIMATE — design default]. Cause-specific: E4 retrieval-decay resolves on the FSRS schedule fix itself succeeding (subsequent spaced reviews correct); E3 missing-prereq resolves only after the BASE concept recovers (E-letter binding assumed enum order [ESTIMATE] until the Slice 1 code read confirms it).
- **Probes:** `probe_card_ids` finally gets a consumer — probe items are injected into the plan (P2.2's probe count), selected on the weak concept near the learner's ability band; what qualifies as a probe item is qcraft's call, consumed here.
- **Mark-Resolved is replaced** by "dismiss for now" (snooze N days): hides the row, cannot set `resolved`, cannot fake mastery, auto-reopens if evidence stays bad. The manual button disappears only after the owner gate approves the auto behavior.

**P2.5 What finally consumes BKT/Elo/calibration + user-facing honesty rules.** Today BKT/Elo/ItemElo/CalibrationBin are display-only or read by nothing [FACT — APP_RECON §3d, risk 9]. This slice gives each a named consumer (nothing is computed without one):
- **BKT P(L)** → gate/regress verdicts (P2.3), weakness flag + auto-resolution evidence (P2.4), mastery snapshots (existing). BKT mastery and FSRS recall stay two side-by-side estimates — BKT assumes no forgetting, so FSRS keeps sole ownership of review scheduling; a high P(L) with low predicted R is precisely the E4 signature, not a contradiction.
- **Elo θ / ItemElo d** → probe and new-card selection: order the new-card allowance and pick probes whose difficulty sits near the learner's band (~80–85% expected-correct acquisition target [ESTIMATE — principled default per learner doctrine, not a human law]); this dial is STRICTLY separate from `desired_retention` (sched's review dial) — no code path may move one from the other.
- **CalibrationBin** → a plan-quality guard: if the day's calibration is grossly off (Brier/logloss beyond a stated threshold [ESTIMATE — default to harden]), the planner freezes model-driven detail and falls back to a plain FSRS-due-only plan, labeled degraded — a valid degraded plan beats a rich broken one. The w-vector re-fit that would fully close this loop stays out of this slice (off-repo worker today [FACT — APP_RECON risk 2]; see BASE44_LOOPS §1 step 3).
- **Honesty rules for anything shown to the user (binding, carried from Slice 1):** the Weakness "confidence" is the fired rule's hardcoded constant (0.4–0.8) [FACT — APP_RECON §4a] — display it as "rule confidence (fixed)" and never as a probability unless/until it is actually computed from evidence; BKT/Elo numbers are labeled model estimates, never measurements; forecast visuals never show completion marks (engage); no pass probability, exam-day recall %, or days-to-mastery figure is ever rendered (sched refusal); every threshold in this slice (0.6 gate, 2-day probe rule, calibration guard) is an unobserved design default shown as such in Slice 1 tooltips and tuned at the owner gate.
